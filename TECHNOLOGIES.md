# Technologies

The project-specific half of the guidance. `CLAUDE.md` and `test/CLAUDE.md` hold rules that are reusable across projects; this file holds what is specific to this project: what it is, the stack, and the commands.

Every library and framework here is a **detail**. Only adapters and the composition root may import them; `domain/` and `application/` never do.

## Project

A personal "second brain": Markdown notes kept in a **separate private GitHub repository**, served through a remote MCP server so every AI client (Claude Code, Claude Desktop, Claude web/phone, ChatGPT) reads and writes the same notes. It runs on the **Cloudflare Workers free plan**. Inspired by YudiG12/second-brain-mcp, but notes live in GitHub instead of Cloudflare Artifacts.

This repository holds only the server code. Notes never go here; the notes repository is reached through configuration.

## Dependency injection

- **No decorators.** Classes in every layer stay free of Inversify. Every binding is a factory: `bind<Port>(SYMBOL).toResolvedValue((dep: Dep) => new Impl(dep), [DEP_SYMBOL])`. This works in Inversify 8 with no decorators and no `reflect-metadata`.
- **One container module per module, next to the code it wires.** Each module has a `<name>.container.ts` exporting a `ContainerModule`, and beside it a `<name>.symbols.ts` with the symbols that container binds. Keep each container small; split it before it grows.
- **Containers live only in outer layers** (`adapters/` or `main/`), never in `domain/` or `application/`.
- **A module built from runtime values** (such as the parsed config) exports a `create<Name>Module(value)` factory from its `<name>.container.ts` instead of a constant. `main/app-modules.ts` builds the full module list from the config.
- **The root container** in `main/` only loads the modules; it holds no bindings of its own.
- **A symbol is declared once**, in the symbols file of the container that binds it. Other containers import it from there.

## Environment

- Typed and validated once, at bootstrap, with a zod schema in `main/`. Every field has its own custom error message, so a missing or invalid variable says exactly which one is wrong and what is expected.
- The rest of the app receives the parsed, typed config through DI, never by reading the environment directly.
- Locally, Bun loads `.env` and wrangler loads `.dev.vars`. `.env.example` and `.dev.vars.example` list every variable with placeholders only (a test keeps them in sync with the schema); copy one and fill it in. Never commit real values.
- `PUBLIC_URL` (required) is the Worker's public origin, with no path or trailing slash. MCP clients connect to `<PUBLIC_URL>/mcp`, which is every token's audience, and GitHub sends users back to `<PUBLIC_URL>/callback`. It must be https, except for loopback hosts.
- `GITHUB_OAUTH_URL` (optional, defaults to `https://github.com`) is where GitHub's OAuth pages live (`/login/oauth/authorize`, `/login/oauth/access_token`). Same https rule. Production leaves it unset; e2e tests point it at the local GitHub fake.
- `GITHUB_API_URL` (optional, defaults to `https://api.github.com`) is the GitHub REST base URL. It must be https, except for loopback hosts (localhost, 127.0.0.1, [::1]). Production leaves it unset; e2e tests point it at the local GitHub fake.
- The schema lives in `src/main/config/env-schema.ts`. `Bootstrap` validates the Worker's env once per env object and throws `InvalidEnvError` listing every problem; the parsed config is bound to `CONFIG_SYMBOLS.AppConfig`. Adapters never import `AppConfig` from `main/`: they depend on the narrow settings interfaces in `src/shared/contracts/` (`NotesRepoSettings`, `OAuthSettings`, `WebhookSettings`), which the config module maps from the parsed config and binds under `CONFIG_SYMBOLS`.

## Sign-in

- `/mcp` sits behind `OAuthProvider` from `@cloudflare/workers-oauth-provider`, built in `src/adapters/inbound/oauth/`. The core knows nothing about it. MCP clients register themselves at `/oauth/register` (dynamic client registration), open `/authorize`, and trade codes for tokens at `/oauth/token`. Client ID Metadata Documents stay off: they need the `global_fetch_strictly_public` flag, which would also stop the Worker from reaching the local GitHub fakes in e2e tests.
- `/authorize` shows a consent page (client name, where access goes, a warning for local apps). Allow sends the browser to GitHub with PKCE (S256); `/callback` exchanges GitHub's code, reads `GET /user`, and completes the authorization only when the account's numeric ID equals `OWNER_GITHUB_ID`. The ID, not the login, because a login can be renamed and then claimed by someone else; the ID never changes. To find yours, open `https://api.github.com/users/<your-login>` and copy `"id"`. Anyone else gets a 403 page and no code. GitHub's token is used once and never stored.
- **The GitHub OAuth app.** On GitHub: Settings → Developer settings → OAuth Apps → New OAuth App (an OAuth App, not a GitHub App).
  - Application name: anything, e.g. `Second brain`. Homepage URL: `PUBLIC_URL`.
  - Authorization callback URL: `<PUBLIC_URL>/callback`, e.g. `https://second-brain-mcp.<your-subdomain>.workers.dev/callback`. For `wrangler dev`, use a second OAuth app with `http://localhost:8787/callback`.
  - Leave Enable Device Flow off.
  - Scopes: none. The Worker asks for no scope, which grants read-only access to public information, enough for `GET /user` to return the login. No `repo` or `read:user` scope is needed: notes are read and written with `GITHUB_TOKEN`, never with the signed-in user's token.
  - Put your numeric GitHub user ID (the `"id"` at `https://api.github.com/users/<your-login>`) in `OWNER_GITHUB_ID`.
  - Copy the Client ID into `GITHUB_CLIENT_ID`, generate a client secret and put it in `GITHUB_CLIENT_SECRET` (`bunx wrangler secret put GITHUB_CLIENT_SECRET` in production).
- **KV namespace.** The provider stores clients, grants and hashed tokens in a KV namespace bound as `OAUTH_KV` in `wrangler.jsonc`. Workers KV is included in the Workers Free plan: 100,000 reads, 1,000 writes, 1,000 deletes and 1,000 lists per day, 1 GB storage (checked 2026-11-19 on developers.cloudflare.com/kv/platform/limits and /pricing). One owner signing in a few times a day stays far below that. `wrangler.jsonc` holds a placeholder `id` until the deploy task creates it with `bunx wrangler kv namespace create OAUTH_KV`.

## Indexing outside the MCP server

Notes edited on GitHub or in Obsidian reach the search index in two ways. Both only queue **paths**: the consumer re-reads each path at the head of the notes branch (or removes it when the note is gone), never trusting the event's content, so late, repeated or out-of-order work still leaves the index matching the repository.

- **Push webhook.** `POST /webhooks/github` checks `X-Hub-Signature-256` (HMAC SHA-256 of the raw body with `GITHUB_WEBHOOK_SECRET`, compared in constant time by `crypto.subtle.verify`), takes only `push` events on `refs/heads/<NOTES_BRANCH>`, and sends the added, modified and removed `.md` paths to the `INDEX_QUEUE`. It answers 202 right away (GitHub allows 10 s). A ping or another event gets 204, a bad or missing signature 401, a non-JSON delivery 415. A force push, or a push at GitHub's caps (2048 commits, 3000 files per commit) whose file lists may be incomplete, runs the reconciliation instead. Set it up on the notes repository: Settings → Webhooks → Add webhook, Payload URL `<PUBLIC_URL>/webhooks/github`, Content type `application/json`, the secret from `GITHUB_WEBHOOK_SECRET`, "Just the push event".
- **Queue consumer.** `second-brain-index` delivers batches of up to 10 messages (2 s wait). Each path goes through `IndexNote` from the head. A failure is logged and retried with backoff (30 s doubling, at most 1 h, or GitHub's `retry-after`); after 5 retries the message goes to the `second-brain-index-dlq` dead-letter queue (created automatically on deploy; it has no consumer, so its messages stay 4 days for inspection). A message with no path, or a path that can never be a note, is acknowledged and logged.
- **Daily reconciliation.** A cron trigger (`17 4 * * *`, UTC) compares the repository tree (path + blob sha) with the `index_manifest` table and queues every note that is missing, stale or orphaned.
- **Free plan fit** (checked 2026-11-19 on developers.cloudflare.com/queues/platform/pricing and /limits, /workers/platform/limits): Queues are included in Workers Free with 10,000 operations a day (a message costs about 3: write, read, delete; each retry one more read) and a fixed **24 h retention**. Retries (30 s to 1 h, 5 at most) finish well inside 24 h, and the daily reconciliation repairs anything a lost message missed. Free allows 5 cron triggers (this uses 1) and 10 ms of CPU per cron run, which fits because the run is mostly waiting on GitHub and D1 and only queues fixes. Notes repositories large enough for GitHub to truncate the tree make the reconciliation run fail with an exception (seen in the Worker logs) rather than guess.
- **Tests.** E2E tests run the consumer in workerd through the real Miniflare queue; under Bun, `harness.getWorker().scheduled()` can't reach the Worker, so `LocalWorker.runDailyCron` calls `scheduled` on `getExport()` instead.

## Test tooling

- Test globals (`describe`, `it`, `test`, `expect`, `beforeEach`, `afterEach`, `beforeAll`, `afterAll`, `jest`) come from Bun with no import. `bun-test.d.ts` in the root types them: `/// <reference types="bun-types/test-globals" />`.
- **Never import values from `bun:test`**: it breaks transpilation. Only type imports are allowed, e.g. `import type { Mock } from "bun:test"`.
- Declare spies and mocks with explicit types, at the top of the test file or in `beforeEach`, e.g. `let save: Mock<NoteRepo["save"]>`.
- Use the Bun globals first. For spies, mocks and time, which Bun only exposes as globals through `jest`, use `jest.fn`, `jest.spyOn`, `jest.setSystemTime`, `jest.useFakeTimers` and the like. Use `jest.*` only for what the other globals don't cover.

- The OAuth provider imports `cloudflare:workers`, which exists only in workerd. `bunfig.toml` preloads `test/shared/adapters/workers-module-shim.ts`, which gives Bun a stand-in module so unit tests can load the Worker's modules.

- **E2E tests run the real Worker in workerd** through wrangler's `createTestHarness` (no extra dependency), started from `test/shared/adapters/local-worker.ts`. Under Bun, the harness URL and `harness.fetch` can't reach the Worker (Bun's `fetch` ignores undici's dispatcher), so requests go through `getWorker().getExport().fetch(request)`, which works. GitHub is the high-fidelity fake served over HTTP by `Bun.serve` (`FakeGitHubServer`), and the Worker reaches it through `GITHUB_API_URL`. Start the Worker once per file (`beforeAll`) and give each test a fresh fake repository (`McpE2eStack.seed`). The same server fakes GitHub's OAuth endpoints (`FakeGitHubOAuth`, reached through `GITHUB_OAUTH_URL`): `McpE2eStack.start` signs in as the owner and hands tests an MCP client with a bearer token. `SignInClient` plays the browser: it keeps cookies and follows redirects by hand, so requests must use `redirect: "manual"` (the harness would otherwise follow them to hosts that don't resolve). `LocalWorker` applies the D1 migrations at start; the search index is shared by the tests of a file, so give each test its own search words. Indexing runs after the reply, so search tests wait for it with `SettledSearch`.

## Commands

- Install: `bun install`
- Run tests: `bun test` (or `bun run test`)
- Run a single test file: `bun test path/to/file.test.ts`
- Run tests by name: `bun test -t "<test name pattern>"`
- Run one test level: `bun test .unit.test` · `bun test .int.test` · `bun test .e2e.test`
- Typecheck: `bunx tsc --noEmit` (or `bun run typecheck`)
- Format: `bun run format` · check only: `bun run format:check`
- Workers runtime and binding types: `bun install` generates `worker-configuration.d.ts` (`postinstall` runs `wrangler types`); after changing `wrangler.jsonc`, run `bun run types`. The file is generated and gitignored: never edit or commit it
- D1 schema: SQL migrations in `migrations/` (wired as `migrations_dir` in `wrangler.jsonc`). Apply them locally with `bunx wrangler d1 migrations apply second-brain --local`; integration tests apply them with `LocalRuntime.migrate()`
- Local dev server: `bun run dev` (`wrangler dev`)
- Deploy: `bun run deploy` (`wrangler deploy`). Not ready yet: `wrangler.jsonc` still has placeholder D1 `database_id` and KV `id` values until the deploy task creates the real resources
